## 1. 一句话需求为什么危险

<img src="imgs/aicmigr-25-autotest-02-plan-breakdown/b697d50d2be97135c98df993c11e3f6c_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

<span style="color: red; font-weight: bold;">一句话需求</span>最大的风险在于：<span style="color: red; font-weight: bold;">它藏的事比说的多得多</span>。一句听起来很具体的需求，背后通常藏着 5~10 个未明确的决策点。不先把它们拍清楚就动手写代码，等于把代码当成需求的探索工具，而改代码的代价是改文档的数倍到数十倍。

### 1.1 一句话需求里藏着什么

先看一个真实需求。RobustMQ 是一个多协议消息中间件，支持主流 MQTT 协议和创新的 mq9 协议，定位生产级。作为开源消息中间件，用户第一个问题不是功能够不够，而是**敢不敢用**：消息会不会丢、节点挂了能不能恢复、客户端 SDK 换个版本还能不能正常连。

这些担心靠单元测试和常规集成测试覆盖不到。现有测试盲区集中在四点：

- 协议兼容性没有持续验证机制
- 故障场景没有系统化覆盖
- 长时间运行问题暴露不出来
- 组合场景几乎没碰

问题发现周期以月计，等用户踩坑再反馈、再修，节奏太慢。所以需要一套自动化的 7×24 不间断混沌测试。

❌ 一句话需求来了：

```
用 AI Agent 给 RobustMQ 实现一套 7×24 不间断跑混沌测试的系统，自动起集群、自动注入故障、自动调多语言 SDK 跑测试、自动收集日志、自动出报告。
```

听起来很具体：5 个功能动词、1 个时间约束、1 个技术取向。但这句话里藏的事，比说出来的多得多：

- [ ] 测什么协议、覆盖哪些 SDK 语言和版本？
- [ ] 故障注入到底是 kill 进程，还是网络延迟，还是磁盘填满？
- [ ] 测试报告给谁看？对内还是对外公开？
- [ ] 多语言 SDK 是预先写好的脚本，还是让 AI 现写？
- [ ] 频率怎么定？所有场景都跑一样频率，还是分级？

每一件都有几种合理选择，每种选择都会影响后面的技术方案。这就是一句话需求的本质：<span style="color: red; font-weight: bold;">表面是一句话，背后是一张未拍板的决策清单</span>。

### 1.2 接到需求的第一件事不是拆方案

你可能会问，既然需求这么明确 —— 起集群、注入故障、收日志、出报告 —— 为什么不直接动手？

原因在于，不先拍清楚就进技术设计，会出现两种典型后果。这两种后果与传统软件工程里"不写需求规格说明书就开工"翻的车一模一样。

#### (1) 写到一半发现假设不对

某个未明确的选择（比如"测试报告对内还是对外"）在不同段落里被默认成不同答案，方案自相矛盾。

- 报告对内，存储可以放本地
- 报告对外公开，就得考虑脱敏、Dashboard、CDN

同一个问题两套默认值，文档写到一半就崩了。

#### (2) 改代码远比改文档贵

不拍清楚就动手，等于把代码当成需求的探索工具。<span style="color: red; font-weight: bold;">代码改一次的代价是文档改一次的数倍到数十倍。</span>文档改一行是改字符，代码改一处要重跑测试、重新部署、回归兼容性，牵动上下游。

**结论**：<span style="color: red; font-weight: bold;">接到一句话需求，第一件事不是拆方案，而是先把需求本身拆完整</span>。把那张未拍板的决策清单列出来、逐项拍掉。这就是接下来要讲的"两次翻译"要做的事。

## 2. 方法总览：两次翻译

<img src="imgs/aicmigr-25-autotest-02-plan-breakdown/585f9c828a41d96fcfe3ef6df809a1aa_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

第 1 章的结论是：接到一句话需求，第一件事不是拆方案，而是先把需求本身拆完整。怎么拆？做法叫**两次翻译**。这个名字本身就在用传统软件工程的概念做类比 —— 把一句话需求"翻译"成可开干的方案，分两次完成：

- <span style="color: red; font-weight: bold;">第一次翻译</span> ≈ 传统需求规格说明书，但<span style="color: red; font-weight: bold;">补全了所有隐藏决策</span>
- <span style="color: red; font-weight: bold;">第二次翻译</span> ≈ 概要设计 + 详细设计，把方案<span style="color: red; font-weight: bold;">落到具体技术栈</span>

如果你熟悉瀑布流程，可以先把两次翻译理解为"需求文档 + 设计文档"这套老组合的升级版。

差别在于：

- 传统需求文档常常写得含糊，把决策推给开发
- 两次翻译的产物把所有隐藏决策都拍死在纸面上，下游不再有"你觉得呢"的空间。

两次产物合起来，构成后续开发的<span style="color: red; font-weight: bold;">单一事实源</span> —— 类似接口契约的角色：**不是开发完成后补的文档**，而是**开发过程中的硬约束**。

### 2.1 两次翻译做什么

两次翻译各自的产物特征：

| 维度      | 第一次翻译                 | 第二次翻译                       |
| ------- | --------------------- | --------------------------- |
| 输入      | 一句话需求                 | 完整设计文档                      |
| 产物      | 完整设计文档                | 完整方案文档                      |
| 是否绑定技术栈 | 否                     | 是                           |
| 核心问题    | <span style="color: red; font-weight: bold;">为什么做、做什么、不做什么、按什么思路</span>   | <span style="color: red; font-weight: bold;">Skill 怎么设计、Tool 怎么实现、场景库怎么放</span> |
| 可分配性    | 还不能直接开发               | 可分配给工程师开干                   |
| 反问模式    | 展开式（"给我两三个选项和影响，我来拍"） | 收敛式（"别又冒新决策，把这版收紧"）         |

**关键差异**：第二次翻译开始前必须先反问"路径选对了吗"，质疑第一次翻译里 AI 顺手给的执行路径。这一步是第二次翻译的灵魂，第 4 章会详细展开。

### 2.2 两次产物构成单一事实源

凭什么两份文档就是硬约束？答案在于它们之间有清晰的因果链：<span style="color: red; font-weight: bold;">设计文档里的每条需求决策，直接决定方案文档里的工程实现。后续每一行代码、每一个配置、每一个判断，都能追溯到上游某条需求决策</span>。这跟接口契约的作用一样 —— 调用方和被调用方都按契约实现，谁偏离谁就是 bug。

这条因果链的实际用法：

- 开发过程中有人问"为什么 `run_client` 要支持 SDK 版本切换"，答案不是"我觉得这样好"，而是"设计文档里这么定的"。
- 改协议兼容性策略时，立刻知道下游哪些 Tool 会受影响。

具体的因果链映射会在第 5 章展开。这里先记住一点：**这两份文档就是开发的硬约束**。任何代码偏离文档，要么改代码，要么改文档，然后回来重新对齐。第 3 章先看第一次翻译具体怎么做。

## 3. 第一次翻译：让 AI 穷举，人来拍方向

第一次翻译的目标用一句话讲清：<span style="color: red; font-weight: bold;">让 AI 穷举该拍的事，由人拍方向</span>。产物与技术栈无关，只讲"为什么做、做什么、不做什么、按什么思路、覆盖什么场景、产出什么"。

这个过程很像传统软件工程里给需求分析师下需求 —— 分析师穷举方案，但方向由 PM 来拍。差别在于，AI 替代了分析师的穷举位，而"拍方向"这件事依然只能由人做，因为只有人知道项目定位和社区接受度。

### 3.1 抛展开提示词

<img src="imgs/aicmigr-25-autotest-02-plan-breakdown/61abbf00db7fd3a305ae8526fdf92687_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">
#### (1) 提示词

打开 Claude Code，给它这样一段提示词：

```
帮我把这个一句话需求展开成完整的技术设计文档：用 AI Agent 给 RobustMQ
实现 7×24 不间断跑混沌测试的系统，自动起集群、注入故障、跑多语言 SDK、
收日志、出报告。

这一步先别谈具体技术框架，把"为什么要做、做什么、不做什么、用什么思路、
覆盖什么场景、产出什么"讲清楚。

有几个我自己一时拍不准的关键选择，你列出来给我看，每个给两三个选项和
影响，我来拍。

不要复述，要展开。
```

#### (2) 提示词的关键设计

提示词里有三处关键设计。

##### ① "先别谈具体技术框架"

把<span style="color: red; font-weight: bold;">问题域</span>和方案分开，<span style="color: red; font-weight: bold;">问题域</span> —— 这是第一次翻译的核心动作。不强调的话，AI 立刻就会往具体框架上跳，结果是在你还没想清楚"要解决什么问题"时，它已经把 Kafka 还是 RabbitMQ 抛在你面前了。

##### ② "几个我拍不准的选择，列出来给我"

这一步真正的灵魂。<span style="color: red; font-weight: bold;">完整设计不是 AI 写出来的，是 AI 帮你列选项、人来拍出来的</span>。 <span style="text-decoration: underline;">AI 不知道项目定位、社区接受度，这些只有人能拍</span>。这句话把"拍不准"的部分显式交还给 AI 穷举，AI 负责"给选项"，人负责"做选择"。

##### ③ "不要复述，要展开"

堵掉 AI 把一句话改写成几句话就交差的偷懒回答。复述是把已知的话换个说法再说一遍，<span style="color: red; font-weight: bold;">展开是把没说清的维度补出来</span>。

#### (3) 提示词评估标准

好提示词的判定标准可以浓缩成一张表：

| 标准                                                      | 说明                                                                            |
| ------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 长度                                                      | <span style="color: red; font-weight: bold;">四五句话即可</span>，模板化的二十行反而限制 AI     |
| 预设                                                      | 把你<span style="color: red; font-weight: bold;">已经想清楚的边界写进去</span>（如"先别谈技术框架"） |
| 余地                                                      | 把你<span style="color: red; font-weight: bold;">拍不准的明确交给 AI 列选项</span>         |
| <span style="color: red; font-weight: bold;">防偷懒</span> | 例如、显式写"不要复述，要展开"                                                              |
| 写作对象                                                    | 给一个<span style="color: red; font-weight: bold;">具体场景</span>（如"能拿出去给社区评审"）     |

### 3.2 拿完整设计预期比对初版

Claude Code 跑完，给出一份完整的设计文档。

关键产物包括：

| 产物段             | 内容                                                                                                                                                      |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **背景段**         | 把 RobustMQ 面临的质量挑战讲清楚<br>- 多协议<br>- 多语言 SDK<br>- 生产级要求                                                                                                  |
| **目标段**         | 提了三条<br>- 自动发现问题加速修复<br>- 公开测试过程建立社区信任<br>- 系统化解决协议兼容性                                                                                                  |
| **系统设计段（最有价值）** | 把核心思路定在"混沌工程的思路 + 全流程 AI 自动化"<br>- AI Agent 是大脑：读场景、定执行顺序、按中间结果动态调整、生成报告<br>- 工具集是手脚：执行集群操作、故障注入、日志收集<br>- 没有 hardcode 的执行流程，AI 驱动一切                    |
| **实现路径**        | Claude API tool use + 若干 Python 工具函数<br><br>不引入 LangGraph、CrewAI 这类 Agent 框架<br>- 这些框架解决的是多 Agent 协作问题<br>- 本系统是单 Agent + 固定工具集，直接用原生 tool use 更简单      |
| **工具集**         | 列了 7 个工具，签名和职责都写齐了<br>- `cluster_start`<br>- `cluster_stop`<br>- `inject_fault`<br>- `run_client`<br>- `get_logs`<br>- `get_metrics`<br>- `push_report` |
| **场景库**         | 给出完整的 MQTT 和 mq9 场景列表，按基础、故障、客户端异常、组合分类                                                                                                                 |

但看完依然觉得有几处空洞。这里的关键动作是：**<span style="color: red; font-weight: bold;">拿一份"完整设计该长什么样"的预期去比对初版，差什么就反问什么</span>**。<span style="color: red; font-weight: bold;">预期从工作经验里来</span> —— 你脑子里得先有一份"完整设计长什么样"的参照系，才能一眼看出 AI 哪里漏了。

### 3.3 反问（不是追问）三处空洞

<img src="imgs/aicmigr-25-autotest-02-plan-breakdown/95efc88c27e788ce01d973785f179115_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

那能不能直接追问呢？不能。追问只是让 AI 把前文再展开一遍，篇幅变大但洞没补上。真正能补洞的是<span style="color: red; font-weight: bold;">反问</span>——你指出它漏了什么，要求它把这一版补完整。

#### (1) 反问提示词

先把这三条直接抛给 Claude Code：

```
你这版有几处空洞：

1. 场景优先级没分。混沌测试持续跑，得有 P0/P1/P2 这种分级，
   按触发频率匹配。补一下。
2. 测试报告对内还是对外？这件事影响存储、Dashboard、脱敏一系列设计。
   给我两三个选项，我来拍。
3. SDK 矩阵不够系统。具体覆盖哪些语言、每种语言哪几个版本、
   怎么切换版本，展开。

别又冒新选择，把这版补完整。
```

#### (2) 三处空洞

内容如下，都来自项目的实际需要，对应用场景和需求深入理解、才会顺口问出。

##### ① 场景的优先级没分

AI 列了几十个场景，但没说哪些每次必跑、哪些每天跑、哪些每周跑。混沌测试持续运行，频率分级是必须的，不然要么**资源**跑爆，要么覆盖度不够。

##### ② 测试报告的公开度没定

报告对内给团队看，还是对外公开？这件事直接决定数据存在哪、有没有 Dashboard、要不要做信息脱敏。

##### ③ SDK 矩阵没系统化

AI 列了"多语言 SDK"，但具体覆盖哪些语言、每种语言哪几个版本、版本之间怎么切换，没讲。协议兼容性测试的核心就是这个矩阵，矩阵不清楚，测试就跑不出可信结果。

#### (3) 反问 vs 追问：一个关键技能

注意尾句<span style="color: red; font-weight: bold;">别又冒新选择，把这版补完整</span> —— 这是反问而不是追问。这两件事经常被混淆，但效果完全不同：

| 维度     | 反问         | 追问           |
| ------ | ---------- | ------------ |
| 触发原因   | <span style="color: red; font-weight: bold;">拿预期比对发现漏了</span>  | <span style="color: red; font-weight: bold;">想多听一遍前文</span>      |
| 典型表达   | <span style="color: red; font-weight: bold;">"你这里漏了，补上"</span> | <span style="color: red; font-weight: bold;">"你前面那段再讲讲"</span>   |
| 对产物的影响 | <span style="color: red; font-weight: bold;">把完整度补齐</span>     | <span style="color: red; font-weight: bold;">增加篇幅但不补洞</span>     |
| 谁主导    | <span style="color: red; font-weight: bold;">人（凭经验判断漏点）</span> | <span style="color: red; font-weight: bold;">AI（凭上下文继续展开）</span> |

**关键判断**：<span style="color: red; font-weight: bold;">AI 不会主动告诉你它漏了什么。能不能反问到位，取决于人脑里有没有"完整设计该长什么样"的预期。</span>

### 3.4 整合成可评审的完整设计文档

Claude Code 跑完，三处全补上。

#### (1) 场景库分级 P0/P1/P2

### 4.4 Skill 套件设计与 Tool 实现要点

#### (1) Skill 套件设计

7 个工具函数全部映<span style="color: red; font-weight: bold;">射成同一个 Skill 套件</span> `robustmq-chaos-test` 下的 Tools。核心理由是它们<span style="color: red; font-weight: bold;">共享同一个上下文（场景描述、集群状态、测试进度），由 Agent 串联调用最自然</span>。如果拆成 7 个独立 Skill，跨 Skill 的上下文管理会成为新的负担。

`SKILL.md` 是 Agent 真正读到的"场景描述"。它告诉 Agent 这个 Skill 是干什么的、有哪些 Tool 可用、什么时候该用哪个、报告应该长什么样。

#### (2) 目录结构

```

├── SKILL.md
├── tools/
│   ├── cluster.py
│   ├── chaos.py
│   ├── client.py
│   ├── observability.py
│   └── report.py
├── scenarios/
│   ├── mqtt/
│   └── mq9/
├── templates/
│   └── report.md.j2
└── config.yml

#### (3) 关键 Tool 设计要点

##### ① cluster_start：不引入 Docker

直接 spawn 多个 RobustMQ 进程。每个节点用独立端口和数据目录，数据目录用临时目录，`cluster_stop` 时清理。这一条决策极简 —— 单机环境跑混沌测试，Docker 反而增加复杂度。

##### ② inject_fault：chaosd 主，tc/kill 补

以 chaosd（Chaos Mesh 单机版）为主，tc / kill 等系统命令为补充。chaosd 提供 HTTP API，函数封装调用，参数对齐 chaosd schema。

| 工具                      | 注入方式                             | 典型故障场景             |
| ----------------------- | -------------------------------- | ------------------ |
| **chaosd**              | 通过 HTTP API 调用，参数化注入进程级、IO、网络等故障 | 进程 kill、IO 注入、网络故障 |
| **tc（traffic control）** | 通过 `tc qdisc` 操纵内核排队规则，直接作用于网卡接口 | 网络延迟、丢包、带宽限制       |
| **kill**                | 直接发送信号（SIGKILL / SIGTERM）终止进程    | 进程崩溃、节点宕机          |

##### ③ run_client：本地版本管理工具切换

服务器上预装多语言运行时和版本管理工具（pyenv / gvm / rustup / sdkman / nvm），skill 里通过版本管理工具切换，不用 Docker。单机环境足够，启动快。

##### ④ push_report：git push 到 GitHub 公开仓库

直接 `git clone` / `commit` / `push` 到 GitHub 公开仓库，不调 GitHub API，比 API 调用更简单可控。

##### ① Skill 边界原则

一个 Skill 套件等于一个独立的工作流。

- chaos-test 是"跑混沌测试"这个工作流；
- 未来 Claude Code 深度分析是"分析失败报告"这个独立工作流

两者通过共享报告仓库联动，但 Skill 内部隔离，不共享 tools 目录。这一条让未来扩展有了明确的界限。

##### ② 故障注入选型标准

- **chaosd**：用于所有需要精确控制的故障（进程级 kill 信号、网络精确延迟分布、磁盘 I/O 限速、时钟穿越）
- **tc / kill**：用于极简快验证场景，临时拉起验证一下逻辑就行

判断标准是"**故障是否需要被精确测量和回放**" —— 需要就用 chaosd，只是验证可达性就用 tc / kill 这类系统自带的命令。

##### ③ GitHub 凭据

用 Deploy Key，只授写权限到 test-reports 单一仓库。

私钥放在服务器 `~/.ssh/test-reports-deploy`，skill 里通过 `GIT_SSH_COMMAND` 环境变量指定使用这个 key 做 git push，不进 Hermes 的 `.env`，也不进版本库。

这一条接住了上一篇那条硬规则：**7×24 无人值守最容易翻车的就是凭据和 allowlist**。

cluster → observability → run_client → inject_fault → push_report
```

再写场景库，最后跑通完整闭环和报告系统。每一步产出都能独立验证，卡在哪一步立刻能定位。

完整方案文档如下： https://robustmq.com/zh/Blogs/95 （内容篇幅有限，就不全贴进来了）。

到这里，第二次翻译做完了。手上拿着的不再是"在 Hermes 上做一个混沌测试系统"这种模糊方向，是一份可以分配给具体工程师按依赖顺序开干的方案。

#### (4) 收敛式反问 vs 展开式反问

两次翻译的反问模式刻意做出了对照：

| 翻译阶段 | 反问模式 | 典型提示词尾句 |
|---|---|---|
| 第一次翻译 | 展开式 | "给我两三个选项和影响，我来拍" |
| 第二次翻译 | 收敛式 | "别又冒新决策，把这版收紧" |

<span style="color: red; font-weight: bold;">展开式让 AI 穷举、人来拍方向；收敛式堵掉 AI 冒新决策、把方案锁定。两次翻译用错模式，要么穷举不充分，要么方案永远定不下来</span>。

## 5. 落地与反思：因果链与放下

<img src="imgs/aicmigr-25-autotest-02-plan-breakdown/88c180feea0c5620c7f72a942a1475d4_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

走完两次翻译，手上有两份真实的文档：**完整设计文档**讲清楚为什么做、做什么、按什么思路；**完整方案文档**讲清楚怎么具体落到 Hermes 上。这一章讲这两份文档怎么用、整套打法怎么记住，以及动手前夜为什么还要"放下"。

### 5.1 决策到实现的映射

这两份文档之间有一条清晰的因果链：设计文档里的每条需求决策，直接决定方案文档里的工程实现。

| 设计文档决策            | 方案文档落地                                                 |
| ----------------- | ------------------------------------------------------ |
| 协议兼容性是核心命题        | `run_client` Tool 的多语言 SDK 矩阵设计                        |
| 测试记录完全公开建立社区信任    | `push_report` 提交到 GitHub 公开仓库 + Quality Dashboard 静态读取 |
| P0 / P1 / P2 场景分级 | `cron.yml` 那 4 条不同频率的触发配置                              |

这条因果链是这两份文档真正的价值。不是文档本身有多漂亮，而是后续<span style="color: red; font-weight: bold;">每一行代码</span>、<span style="color: red; font-weight: bold;">每一个配置</span>、<span style="color: red; font-weight: bold;">每一个判断</span>，都能追溯到上游某条需求决策。

传统软件工程里有"需求追溯矩阵"，用来在交付后反向核对每条需求是否被实现。这里的因果链比追溯矩阵更前置 —— 它不是事后核对，而是在设计阶段就建立起来的硬约束：开发过程中如果有人问"为什么 `run_client` 要支持 SDK 版本切换"，答案不是"我觉得这样好"，而是"因为设计文档里的协议兼容性目标这么定的"；如果某天需要改协议兼容性策略，也能立刻知道下游有哪些 Tool 会受影响。

接下来开发的时候，这两份文档就是<span style="color: red; font-weight: bold;">单一事实源</span>—— <span style="color: red; font-weight: bold;">不是开发完成后再补的文档</span>，<span style="color: red; font-weight: bold;">而是开发过程中的硬约束</span>。

第 2 章讲两次翻译产物合起来构成单一事实源、扮演类似接口契约的角色，到这里闭环了：任何代码偏离了文档的决定，要么改代码，要么改文档，然后回来重新对齐。

### 5.2 项目阶段 Check List

把整套打法浓缩成一张可裁剪的实操清单：

| 项目阶段 | 关键动作 | 产物 | 反问点 |
|---|---|---|---|
| 接到一句话需求 | 不立刻拆方案；先列出需求里藏的决策点 | 隐藏决策清单 | 这句话里哪些事没说清？ |
| 第一次翻译 · 抛提示词 | 预设 + 余地；先别谈技术框架 | 展开提示词 | 提示词是否堵住了 AI 偷懒？ |
| 第一次翻译 · 比对初版 | 拿完整设计预期去比对 | 漏点清单 | 哪些维度 AI 没列？ |
| 第一次翻译 · 反问补齐 | 反问（不是追问） | 补齐后的设计文档 | 还能继续反问吗？ |
| 第一次翻译完成 | 整合成可对外评审文档 | 完整设计文档 | 文档能让外部工程师读懂吗？ |
| 第二次翻译 · 路径反问 | "路径选对了吗" | 路径对照表 | 已有工具能复用多少？ |
| 第二次翻译 · 演进评估 | 评估未来演进空间 | 演进收益分析 | 自研路径的天花板在哪？ |
| 第二次翻译 · 收紧反问 | "别又冒新决策" | 完整方案文档 | 还有哪些点没收紧？ |
| 方案落地后 | 文档即硬约束；偏离则改代码或改文档 | 单一事实源 | 每行代码能否追溯到上游需求？ |
| 动手前夜 | 放下文档一晚，第二天再看 | 修订后的两份文档 | 哪个决策当时拍得太草率？ |

#### (1) 两次翻译口诀

把整套方法论浓缩为口诀，按项目时间线依次执行：

```
一句话需求藏的事，比说的多。
接到先翻译两次，再动手。

第一次翻译：让 AI 穷举该拍的事，人来拍方向。
          产物与技术栈无关，讲清为什么做、做什么、不做什么。
第二次翻译：先反问"路径选对了吗"，再落到技术栈。
          产物可分配开干，包含 Skill/Tool/场景/触发配置。

每次翻译都反问到收敛为止。
AI 的价值是穷举，人的价值是拍方向。
最后留一晚沉淀，第二天再回头改。
```

为什么接到需求当天就开始写代码的人没一个交付得好？理由不是"先写文档显得专业"，而是**写文档的过程本身就是把需求里所有藏着的事拍清楚的过程**。不拍清楚就动手，等于把代码当成需求的探索工具，代价是改代码远比改文档贵。

### 5.3 留一晚给方案沉淀

写完两份文档，为什么还不能动手？回到第 1 章那句老话——代码改一次的代价是文档的数倍。文档已经写完，但写文档的过程本身消耗了一种隐形成本：你的判断力。

第一次翻译和第二次翻译的每一次反问，都在消耗"当时的判断力"。反问到收敛，意味着你已经连续做了大量方向性决策：协议兼容性怎么定、场景怎么分级、路径选自研还是复用、触发频率怎么排布。每一拍都消耗判断力，而判断力不是无限的资源。<span style="color: red; font-weight: bold;">判断力疲劳时拍出的决策，第二天看往往能立刻发现偏差。</span>

所以写完两份文档，第一件事其实是**放下**。第二天早上再看一遍，常常会发现某个决策当时拍得太草率，趁还没动手赶紧改回来。<span style="color: red; font-weight: bold;">一晚上的间隔让大脑从"穷举模式"切回"审视模式"，再回头看方案，往往能挑出前一天挑不出来的问题</span>。<span style="color: red; font-weight: bold;">真正动手前，留一晚给方案沉淀——这条经验比方法论本身值钱</span>。
