本篇接续系列第 03 篇《让 AI 可信的三层控制》。上一篇把"理解、约束、验证"三层骨架立起来；本篇回答随之而来的下一个问题：市面上 Claude Code、Cursor、Copilot、CLAUDE.md、AGENTS.md、SKILL.md、Spec-Kit、Kiro、MCP、Sourcegraph、SonarQube、SDD、Harness 一连串概念怎么归类、哪些是主战场、哪些是旁支。

这是系列方法论基础的第四篇。前三篇分别回答了"做什么"（九步链路）、"AI 做多少"（三档分工）、"怎么让 AI 不乱来"（三层控制）。本篇收口方法论基础，回答最后一个偏选型的问题：工具那么多，到底该学哪几件。

翻开任何一篇 AI 编程文章，都能撞见一堆新名词。今天冒出一个 Spec-Kit，明天出一个 Kiro，后天某个 MCP Server 又刷屏。每件工具都标榜"让 AI 编程更高效"，每件都声称"非学不可"。工程师面对这片工具海，常见的反应有两种：

- **什么都学**：跟风装一遍，每个都浅尝辄止。结果真坐下来改造老项目，发现还是只用了那一个 AI 编码 Agent，其他工具只是占着硬盘。
- **什么都不学**：被工具更新速度吓退，干脆只用最熟的一件。结果错过了几个真能提速的关键辅助。

两种反应都没抓住要害。真正缺的不是工具清单，是一张<span style="color: red; font-weight: bold;">能归类、能校准、能判断价值的地图</span>。拿到一件新工具，先问三句话——它属于哪类、解决三层骨架哪一层的问题、相比现在用的工具有什么增量价值——再决定要不要花时间。本篇要给的，就是这张地图，加上判断的动作。读完本篇，工程师拿到一张 AI 编程工具的武器库地图，从此面对层出不穷的新工具，能立刻判断它属于哪类、解决的是三层骨架哪一层的问题、值不值得花时间学。

## 1. 工具多到眼花：怎么归类

### 1.1 一长串名字砸过来，先别慌

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/04c1896cfaefdb715258096247bfca95_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

翻开任何一篇 AI 编程的文章，迎面就是一串名词——Claude Code、Cursor、Copilot、Cline、Aider、CLAUDE.md、AGENTS.md、.cursorrules、SKILL.md、Spec-Kit、Kiro、Tessl、OpenSpec、MCP、Sourcegraph、SonarQube、各类 MCP Server……哪个该学，哪个可以忽略？

这种场面传统工程师并不陌生。第一次走进一座大型军火库的人也是同样的表情——主武器、辅助装备、防护工具、备件混在架子上，标签没看明白前不敢伸手。"伸手前先看标牌"恰恰是传统工程师的强项。

#### (1) 老工程师的优势：你已经会分类

打开一个新项目，你不会把 IDE、构建工具、依赖管理、CI、监控混为一谈——你会先按"它们各自解决什么问题"分个堆。AI 编程工具同理：<span style="color: red; font-weight: bold;">分类的标尺不是"叫什么名字"，而是"它解决的是哪一类问题"</span>。

> 类比的锚点：把这一堆工具当作一座 AI 编程的军火库。要做的不是记住每件武器的型号，而是先看清每件武器挂在哪个分区。

#### (2) 收获预告：读完本章带走三样东西

| 收获     | 具体内容                                                                   |
| ------ | ---------------------------------------------------------------------- |
| 一张地图   | 把主流 AI 编程工具按解决的问题分成五类，新工具冒出来能立刻归位                                      |
| 一组判断动作 | 按场景选武器的判断动作（主武器永远是 AI 编码 Agent，辅武器按场景复杂度加减——第 2 章展开）                   |
| 一条心法   | <span style="color: red; font-weight: bold;">工具不是学得越多越好，是"够用就停"</span> |

地图先在这里摊开。

### 1.2 一张地图：按"解决的问题"分五类

分类的标尺为什么是"解决的问题"，而不是"是不是 AI""开不开源""收不收费"？

因为工程师选武器的真实动作是"我现在卡在哪一层"——是 AI 看不懂项目？是 AI 改了不该改的地方？还是 AI 写完没人验收？这些"问题维度"才是选型的真实坐标。按名字、按出身分反而会越分越乱。

#### (1) 五类划分速查表

下面这张总览表把五类工具的核心定位、对应到第 03 篇"三层骨架"的哪一层、关键代表摆在一起，是全章的速查入口。对"三层骨架"还不熟的读者，先记一个粗略映射：理解层管"AI 看懂项目"、约束层管"AI 不乱改"、验证层管"AI 产出兜底"。

| 类别          | 一句话定义                       | 对应三层骨架    | 代表工具                                                                                             |
| ----------- | --------------------------- | --------- | ------------------------------------------------------------------------------------------------ |
| AI 编码 Agent | 跟 AI 打交道的主入口                | 三层都在用     | Claude Code、Cursor、Copilot、Cline、Aider                                                           |
| 上下文管理       | 把上下文从"临时说一遍"变成"常驻 AI 自动读"   | 理解层 + 约束层 | CLAUDE.md、AGENTS.md、.cursorrules、SKILL.md、各类 Memory Bank                                         |
| 能力扩展        | 让 AI 从"只能看代码"升级到"<span style="color: red; font-weight: bold;">能看代码之外的东西</span>" | 理解层       | MCP、<span style="color: red; font-weight: bold;">Sourcegraph</span>、各类 <span style="color: red; font-weight: bold;">MCP Server</span>（Github、数据库、内部） |
| 规范驱动开发（SDD） | 先写规范再写代码                    | 约束层       | Spec-Kit、Kiro、Tessl、OpenSpec                                                                     |
| 工程辅助        | 给 AI 的产出兜底                  | 验证层       | SonarQube、测试框架、CI/CD、cross-provider review                                                       |

图里能看出一个关键布局：<span style="color: red; font-weight: bold;">AI 编码 Agent 是唯一贯穿三层的主武器，其余四类都是辅助武器</span>，按"理解/约束/验证"三层各归各位。这也是下面逐类展开的顺序依据。

### 1.3 逐类展开：每类解决什么问题

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/1b9d81dd968e24c1c7eeb012b445e8d8_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

地图摊开了。每一类具体长什么样、和三层骨架怎么对应？下面逐类走一遍，每类只回答三个问题——它解决什么问题、典型形态有哪些、和本文主线什么关系。

#### (1) 第一类：AI 编码 Agent（主武器）

这一类是工程师和 AI 打交道的主入口，所有对话、改代码、跑命令都从这里发起。

为什么 IDE 内置型和命令行型要分两支？因为它们决定了你和 AI 协作的工作姿势——一个贴着编辑器，一个贴着终端。

| 形态      | 代表工具                 | 工作方式              |
| ------- | -------------------- | ----------------- |
| IDE 内置型 | Cursor、Copilot、Cline | 在编辑器里直接对话、直接改代码   |
| 命令行型    | Claude Code、Aider    | 在终端里开一个会话，用自然语言指挥 |

选型上有一个反常识的判断：这类工具选一个就够。本文全程用 Claude Code，不是因为它唯一，是因为它在老项目改造这个场景下最顺手。换其他工具（例如 CodeX）效果基本一样——主武器形态不同，方法论可以平移。

> 类比的锚点：AI 编码 Agent 就像 IDE 本身——你不会同时开三个 IDE 写同一个项目，主武器选定一个就专心用熟。它的迭代频率、快捷键、工作流习惯才是真正的生产力。

和主线对应：它是三层骨架的"操作面"，理解层、约束层、验证层的动作最终都通过它执行。

#### (2) 第二类：上下文管理（老项目改造最核心的辅助）

光有 AI Agent 不够。工程师得告诉 AI 这个项目是什么、哪些地方不能动、哪些规矩要守。这一类是老项目改造最核心的辅助武器——第 03 篇三层骨架里理解层和约束层的大部分动作都落在这里。

CLAUDE.md、AGENTS.md、.cursorrules、SKILL.md 这些名字看起来都差不多，到底什么区别？答案是"格式约定不同，解决的是同一类问题"——把项目上下文固化成文件让 AI 自动读。

| 形式           | 归属工具/工具族                                                                           | 角色                                                                 | 传统工程类比                                                           |
| ------------ | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| CLAUDE.md    | Claude Code                                                                        | 项目级上下文文件                                                           | 项目内部 Wiki                                                        |
| AGENTS.md    | 其他 Agent 工具                                                                        | 类似的上下文约定                                                           | 跨工具通用版项目 Wiki                                                    |
| .cursorrules | Cursor                                                                             | 规则文件                                                               | 编辑器配置 + 团队规约                                                     |
| SKILL.md     | Claude Code 等                                                                      | <span style="color: red; font-weight: bold;">专项技能文件（本文重度使用）</span> | <span style="color: red; font-weight: bold;">团队 SOP 手册</span>    |
| 各类记忆系统       | <span style="color: red; font-weight: bold;">Cline Memory Bank、MemGPT、Zep 等</span> | <span style="color: red; font-weight: bold;">跨会话持久化记忆</span>       | <span style="color: red; font-weight: bold;">项目知识库 + 会话存档</span> |

> 共同特点：把上下文从"每次对话临时说一遍"变成"常驻在项目里 AI 自动读"。一次写好，后面每次会话都自动加载，不用重复讲。

和主线对应：理解层（让 AI 看懂项目）和约束层（让 AI 守规矩）都重度依赖这一类。后面会花大量篇幅讲 CLAUDE.md 和 SKILL.md 怎么写。

#### (3) 第三类：能力扩展（有用但不是必需）

AI 默认只能读代码。让它做别的事，需要扩展。这一类就是给 AI 装"外挂感官"。

MCP 到底是什么？一句话——给 AI 接外部能力的标准协议，类似传统后端服务调用第三方 API 时的 SDK 约定，只不过这里被调用方是 AI。

| 扩展方向 | 代表工具                                                                           | 让 AI 多看见什么                                                       |
| ---- | ------------------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 通用协议 | MCP（Model Context Protocol）                                                    | 给 AI 接外部能力的标准协议                                                  |
| 代码搜索 | <span style="color: red; font-weight: bold;">Sourcegraph</span>                | <span style="color: red; font-weight: bold;">跨仓库代码搜索、依赖分析</span> |
| 协作历史 | <span style="color: red; font-weight: bold;">GitHub / GitLab MCP</span> Server | PR、issue、commit 历史                                               |
| 数据查询 | <span style="color: red; font-weight: bold;">数据库 MCP Server</span>                                                                 | <span style="color: red; font-weight: bold;">schema、跑查询</span>   |
| 内部系统 | 企业自建的 MCP Server                                                               | 企业自有的指标、配置、监控                                                    |

> 共同特点：让 AI 从"只能看代码"升级到"能看到代码之外的东西"——历史、依赖、数据库、线上指标都能接进来。老项目改造里这一类有用但不是必需：零 MCP 也能跑完整改造，但接上关键几个 MCP，很多事会快很多。

和主线对应：理解层的"扩音器"。接不接取决于老项目规模——单仓库小项目基本可以不接，跨仓库大型老系统强烈建议接 Sourcegraph 这类。

#### (4) 第四类：规范驱动开发 SDD（知道有这么一类就够）

近一年冒出来的一类。本文不主线讲它，原因下面表格里说清楚。

| 工具 | 出身 | 定位 |
|------|------|------|
| Spec-Kit | GitHub 开源 | spec-driven 开发框架 |
| Kiro | AWS | Agentic IDE，主打规范驱动 |
| Tessl | 商业产品 | 商业 spec-driven |
| OpenSpec | 社区组件 | 相对较轻，适合 brownfield/改造 |

> 共同特点：先写规范再写代码。先定义 spec、验收标准、接口契约，再让 AI 基于 spec 生成代码。类比的锚点：spec ≈ 接口契约，constitution ≈ 架构约束文档。

既然 SDD 听起来很对路，老项目改造为什么不主线用它？<span style="color: red; font-weight: bold;">因为强行给老代码"补 spec"是本末倒置</span>。

| 不主线讲的原因         | 具体说明                              |
| --------------- | --------------------------------- |
| 老项目本来就没有清晰 spec | 给一段老代码强行"补 spec"意义不大              |
| 核心思想已含在第 03 篇   | SDD 的"先约束、再动手"已经在三层控制里，不需要再套流程化的壳 |

知道有这么一类工具就够。将来做新项目，可以正经学一下——第 5 章会展开实战，到那里再回头细看。

和主线对应：约束层的一种"重装版本"，本文用更轻的三层骨架替代了它。

#### (5) 第五类：工程辅助（验证层的主要载体）

最后一类是传统工程工具，不是 AI 时代特有的，但在 AI 协作下重要性被放大了。

SonarQube、测试框架、CI/CD 这些早就用上了，为什么还要在 AI 工具盘点里提一遍？因为 AI 改变了这些工具的权重——它们从"质量保障"升级成"AI 产出的兜底防线"。

| 工具类型                  | 代表                  | 在 AI 协作中的角色         |
| --------------------- | ------------------- | ------------------- |
| 静态代码分析                | SonarQube / Sonar   | 自动发现 AI 产出里的代码异味    |
| 测试框架                  | Jest、JUnit、pytest 等 | 本来就有，AI 时代更关键       |
| CI/CD 集成              | 各类 CI 系统            | 让 AI 产出必须跑过 CI 才能合入 |
| <span style="color: red; font-weight: bold;">Cross-provider review</span> | <span style="color: red; font-weight: bold;">Codex ↔ Claude Code</span> | <span style="color: red; font-weight: bold;">让不同模型互相 review 对方产出</span> |

> 为什么 AI 协作下这一类更重要：AI 写代码的速度远快于人的 review 速度，传统的人肉把关不够了，工程工具必须进来兜底。三层骨架里的验证层，很多动作就落在这一类。

和主线对应：验证层的主要载体。第 6 章会专门讲怎么把 SonarQube、CI、Cross-provider review 串成一道 AI 产出的自动验收流水线。

### 1.4 小结：从"眼花"到"看牌"

回到开头那个问题：一长串名词砸过来怎么办？答案已经就位。

| 动作 | 对应本章内容 |
|------|------------|
| 看到任何新工具，先问"它解决哪一类问题" | 五类划分速查表 |
| 不确定归位时，对照三层骨架找落点 | 三层骨架映射 |
| 拿不准要不要学，先看它是不是主武器或老项目改造核心辅助 | 1.3 节的"和主线对应" |

地图有了，下一个问题自然冒出来：场景来了，从这座武器库里拿哪一件。

## 2. 选武器的心法

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/fdc78a4d95e35c054c16702bb6363db8_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

武器库摊开了，下一个问题是：场景来了，拿哪一件？这一章用一条贯穿所有场景的选型公式回答它，再收窄到四件重度工具，最后给出判断新工具价值的三个动作。

这也是「主武器公式」在全篇唯一详讲的位置——讲透之后，后面章节只落地使用，不再重复。

### 2.1 一条贯穿所有场景的选型公式

怎么把五花八门的工具压缩成一句话就能记住的配比？

先借用你熟悉的老经验。传统软件工程选技术栈，核心框架（比如 Spring Boot）永远固定，辅助库（Lombok、MapStruct、Hutool）按项目复杂度加减——做一个内部小工具，Spring Boot 起一个就行；做一个跨团队的中台系统，再加 Redis 客户端、消息队列客户端、监控埋点。**核心框架永远不变，辅助库按场景加减。**

AI 时代的工具选型是同构的：<span style="color: red; font-weight: bold;">AI 编码 Agent 就是那个永远不变的「核心框架」，其余工具都是「辅助库」</span>。

下面这张表把场景复杂度从低到高排开，标出主武器和辅武器怎么配。

| 场景复杂度                                                            | 主武器                                | 辅武器配置                                                                                         |
| ---------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------------------------------------------- |
| 极低（改一个小 bug）                                                     | AI 编码 Agent                        | 无                                                                                             |
| 中（跨模块的中等改造）                                                      | AI 编码 Agent + CLAUDE.md + SKILL.md | 测试框架 + CI                                                                                     |
| 高（<span style="color: red; font-weight: bold;">接手陌生项目第一天</span>） | AI 编码 Agent                        | 上下文管理 + 能力扩展（<span style="color: red; font-weight: bold;">Sourcegraph MCP</span>）                                                                 |
| 更高（<span style="color: red; font-weight: bold;">陌生语言</span> + 陌生项目）                                                  | AI 编码 Agent + CLAUDE.md            | MCP（GitHub / Sourcegraph）+ <span style="color: red; font-weight: bold;">语言学习助手模式</span>       |
| 最高（<span style="color: red; font-weight: bold;">高风险改造：安全、跨核心服务</span>）                                               | AI 编码 Agent + SKILL.md（专项技能）       | Sourcegraph（找全调用路径）+ <span style="color: red; font-weight: bold;">独立 review（攻击者视角等多角度）</span> |

表里藏着三条规律，每条都反直觉，值得停下看一遍。

第一，**主武器列始终只有 AI 编码 Agent**。从最简单的 bug 改到最高风险的跨服务改造，它从未换过。CLAUDE.md、SKILL.md、MCP 是「附加在主武器上」的装备，不是另一把武器。

第二，**辅武器随复杂度单调增加**。复杂度低时不带，复杂度高时才堆。反过来也成立——简单任务上堆满辅武器，是过度工程。

第三，**风险越高，越要靠「约束」和「验证」补位**。最高一档配的是 SKILL.md（专项约束）+ Sourcegraph（找全调用路径）+ 独立 review（多视角兜底），而不是换一个更强的 Agent。风险场景的正确反应是加约束、加 review，不是换刀。

#### (1) 主武器公式

这三条规律合成一句话，就是贯穿所有场景的选型公式：

> <span style="color: red; font-weight: bold;">主武器固定，辅武器随复杂度加减。</span>记住这一句，比记住一长串工具名有用得多。
>
> 它也顺手回答了一个常见困惑：<span style="color: red; font-weight: bold;">为什么工程师学了一堆工具，真坐下来干活的时候还是只用了那一个 AI 编码 Agent——不是工具学得不够，是场景配比本来就如此</span>。

### 2.2 收窄到四件重度工具

地图铺开了，真要下手学哪几件？

再收窄一步：本文主线会重度使用的就四件。下表把这四件的角色，和「理解—约束—验证」三层骨架的对位关系摆出来。

| 工具 | 角色 | 三层骨架对应 |
|------|------|------------|
| Claude Code | AI 编码 Agent（主武器） | 三层都在用 |
| CLAUDE.md | 项目级上下文 | 理解层 + 约束层 |
| SKILL.md | 专项技能文件 | 约束层 |
| MCP | 按需接入外部能力 | 理解层（用得相对较少，主要是前三件） |

用老经验再做一次映射。这四件 ≈ 传统 Java 开发的固定班底：

| AI 工具       | 传统 Java 类比                     | 共同点           |
| ----------- | ------------------------------ | ------------- |
| Claude Code | IDEA                           | 天天在里面写代码的主力   |
| CLAUDE.md   | 项目 README + 架构约束文档             | 项目知识沉淀、规范说明   |
| SKILL.md    | 团队内部的《XX 业务开发指南》               | 把专项流程沉淀成可复用资产 |
| MCP         | <span style="color: red; font-weight: bold;">IDEA 插件市场里挑的几款（数据库、HTTP、AI 助手）</span> | 按需补能力，不强制     |

你不会因为听说了 50 款新插件就天天换 IDE，也不会因为新出了一个 JPA 替代品就重构整套数据访问层。**主力稳定，插件按需。** AI 工具同理。

#### (1) 老项目改造的核心是把这几件用熟

> <span style="color: red; font-weight: bold;">老项目改造的核心不是工具数量，是把这几件用熟。</span>
>
> <span style="color: red; font-weight: bold;">CLAUDE.md 写到能让 AI 稳定工作，比学会 10 个新工具重要得多。</span>
>
> 判断一个工程师 AI 协作水平有个快指标：看他 CLAUDE.md 写得怎么样。写得清楚的人，工具堆得不多也能稳定产出；写得糊的人，工具再多也会被 AI 带偏。

### 2.3 拿到新工具先问三个问题

新工具层出不穷，怎么不被淹没？

主线之外还有几类「特定场景提到但不是主线」的旁支工具。下表列出它们的定位，帮工程师判断要不要花时间。

| 旁支工具                                        | 在本文中的定位  | 建议                     |
| ------------------------------------------- | -------- | ---------------------- |
| Sourcegraph、SonarQube、Cross-provider review | 特定场景提到   | 知道有，遇到对应场景再用           |
| Spec-Kit、Kiro 等 SDD 工具                      | 不用       | 跟老项目改造主线不对路，先不学        |
| 各种新冒出来的工具                                   | 用武器库地图校准 | 先问属于哪类、解决哪层、相比现用工具有何增量 |

三类旁支对应三种动作：**知道有、不用、校准。**

「知道有」的工具有明确的高价值场景（如 Cross-provider review 做高风险改造的多视角兜底），主线不强求，但你得记得有这把刀。

「不用」的工具不是不好，是和当前主线不对路。<span style="color: red; font-weight: bold;">Spec-Kit、Kiro 这类 SDD 工具更贴合从零起步的新项目，老项目改造的约束、习惯、存量代码都不一样</span>。先放一放。

「校准」针对每周都在冒出来的新工具。不要看到新工具就上手，先放进地图看位置。

#### (1) 三问的具体含义

下表是判断「要不要花时间学新工具」的三个标准动作。任何一个新工具到手，先把这三问跑一遍。

| 问题 | 判断 |
|------|------|
| 它属于武器库哪一类？ | 五类里对号入座 |
| 解决理解、约束、验证哪一层的问题？ | 跟三层骨架对位 |
| 相比现在用的工具有什么增量价值？ | 想清楚再决定要不要花时间学 |

第一问做归类，避免把它当成全新物种——大多数新工具都是旧类目的新成员。

第二问做定位，知道它补的是哪一层。同样是新工具，落在验证层和落在理解层，对你工作流的改动完全不同。

第三问做取舍。增量价值讲得清楚就值得花时间；讲不清楚，多半是已有工具的换皮。

> 不对路的工具，知道有就够。<span style="color: red; font-weight: bold;">地图的核心价值不是让你多学，是帮你画下「可以不学」的边界。</span>
>
> 一个反常识的判断：<span style="color: red; font-weight: bold;">工程师的工具焦虑，往往不是因为学得少，而是因为不知道哪些可以不学——画清这条边界，才是地图的真实价值</span>。

## 3. 项目阶段 Check List

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/907851c021df2f5031fc3f1495b45c7f_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

方法论讲完了，落到日常具体怎么执行？

传统软件发布前，团队都有一份 <span style="color: red; font-weight: bold;">go-live checklist</span>：数据库迁移跑过没、回滚脚本准备好没、监控大盘配上没、值班排班定好没。这些检查点散落在各角色脑子里，checklist 把它们收敛成一张表，谁接手都能照着打勾，不漏关键步骤。

AI 工具栈的配置和它同构。第 1、2 章给出的"主武器 + 上下文 + 能力扩展 + 工程辅助"，<span style="color: red; font-weight: bold;">本质就是改造任务的 go-live checklist</span>。区别只在于：传统 checklist 检查发布前的运维状态，这里检查改造前的工具栈状态。

### 3.1 方法论怎么落到日常

本章按这四类组织清单，每类固定三段：**判定准则**（一句话判断这类配没配齐）→ **勾选表**（两列：勾选项 / 具体做法）→ **层间切换提示**（前一类配齐后，下一类该接什么）。

四类按依赖顺序排：主武器选定 → 上下文管理 → 能力扩展 → 工程辅助。前一类没配齐，后一类配了也白搭。严格按顺序打勾。

### 3.2 主武器选定 Check List

**判定准则：是否为本次改造选定了一个 AI 编码 Agent 并坚持用熟。**

主武器没定，后面三类都是空中楼阁。

| 勾选项 | 具体做法 |
|--------|----------|
| ☐ 选一个就够 | 在 Claude Code、Cursor、Copilot、Cline、Aider 里选一个，推荐 Claude Code |
| ☐ 不要频繁换工具 | 老项目改造是长跑，主武器的肌肉记忆比花样重要 |

传统开发里，你不会今天用 IDEA、明天切 VS Code、后天又换 Vim——主力 IDE 定下来，几年不换。AI 编码 Agent 同理。频繁换工具的代价不是工具本身，是每换一次都要重建肌肉记忆，长跑任务经不起这种消耗。

> 层间切换提示：主武器选定后，下一件事是把项目上下文喂给 AI，进入上下文管理。

### 3.3 上下文管理 Check List

**判定准则：是否把项目级上下文写到了 AI 自动加载的位置。**

AI 编码 Agent 每次会话都是一张白纸，项目背景得你自己喂。喂法不是每次开会话时口头说一遍，而是写到它自动加载的位置——一次写好，长期复用。

| 勾选项 | 具体做法 |
|--------|----------|
| ☐ 写 CLAUDE.md | 把业务场景、架构组织、接口边界、数据模型、隐性约定沉淀进 CLAUDE.md |
| ☐ 识别专项技能写 SKILL.md | 对反复出现的复杂操作（例如"按九步链路画架构"），沉淀成 SKILL.md |
| ☐ 一次写好长期复用 | 上下文管理是静态投资，写一次后面每次会话自动加载，不要每次临时说一遍 |

CLAUDE.md 和 SKILL.md 的分工要分清：CLAUDE.md 是项目级常驻知识（业务背景、架构约定，每次会话都带），像项目的 README 加架构约束文档；SKILL.md 是任务级专项流程（只在执行特定操作时触发），像团队内部的《XX 业务开发指南》。

> 层间切换提示：上下文管理写扎实后，再考虑给 AI 接外部能力，进入能力扩展。

### 3.4 能力扩展 Check List

**判定准则：是否在不破坏主线简洁性的前提下按需接入 MCP。**

上下文喂饱了，AI 已经能稳定干活。常见冲动是把所有能找到的 MCP 都接上，让 AI 无所不能。这个冲动要压住——MCP 是辅助库，不是核心框架，主武器简洁性比能力数量重要。

| 勾选项             | 具体做法                                            |
| --------------- | ----------------------------------------------- |
| ☐ 评估是否真需要 MCP   | 零 MCP 也能跑完一个完整改造，先问"接入这个 MCP 带来的提速值不值得新增的复杂度"   |
| ☐ 优先接高价值的几个     | 代码搜索（Sourcegraph）、协作历史（GitHub MCP）通常 ROI 最高，优先接 |
| ☐ 不接企业内部低价值 MCP | 不是每个企业自建 MCP 都值得接，能用人工查的就先人工查                   |

判定标准是 ROI，不是"能不能接"。每接一个 MCP 都要付配置成本、维护成本、出错时排查成本。代码搜索、协作历史这类每次改造都反复查，ROI 高，优先接；一周才用一次、还经常出问题的企业内部 MCP，先用人工顶住，等真痛了再说。

> 层间切换提示：能力扩展到位后，进入工程辅助兜底验证层。

### 3.5 工程辅助 Check List

**判定准则：是否给 AI 的产出搭起了独立于 AI 的验证网。**

前三类工具都是给 AI 加装备，让它产出更快更多。但 AI 产出越多，单靠人肉把关越兜不住。这一类逻辑反过来——不依赖 AI 自己说"我做对了"，而是搭一张独立于 AI 的验证网，让它必须跑过门禁才能合入。

| 勾选项 | 具体做法 |
|--------|----------|
| ☐ 测试框架先搭起来 | 第 03 篇验证层的"集成测试 + Characterization Test"都要靠测试框架承载 |
| ☐ CI 兜底 | 让 AI 产出必须跑过 CI 才能合入，把人肉把关替换成自动门禁 |
| ☐ 关键节点加独立 review | 高风险改造加 Cross-provider review，让另一个模型从攻击者视角审一遍 |

三层验证手段各管一段：测试框架承载"代码改对了没"的回归；CI 把测试自动化成门禁，AI 改完代码必须自己跑过才能进主干；Cross-provider review 兜高风险场景，让另一个厂商的模型以攻击者视角再审一遍，防止单一模型盲区。三层叠起来，AI 产出的质量才有独立保证，不再靠工程师熬夜盯 diff。

> 层间切换提示：四件主线工具加上工程辅助兜底，构成完整的工具栈。下一章把这套配置放回真实场景做实战演示。

## 4. 场景落地：五大场景的武器组合

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/6b5ec251838a870dacdfe9b6066383ae_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

第 3 章定了主线四件套。但同一件工具，放在改 bug 和改核心服务里用法天差地别。本章把这套配置放回真实场景，看五大场景下武器组合怎么配、四件主线工具怎么协作、为什么是它们。

### 4.1 五大场景武器组合总览

第 3 章的选型公式已经定了「主武器固定，辅武器随复杂度加减」。本节把公式落到五个典型场景，看每个场景具体配什么。

下表把五个场景的「目标—主武器—辅武器—当日产出」摆在一起，一眼看完。

| 场景              | 目标                                                                          | 主武器                                | 辅武器                                                                                                                                                  | 当日产出               |
| --------------- | --------------------------------------------------------------------------- | ---------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 接手陌生项目第一天       | 让 AI 帮你<span style="color: red; font-weight: bold;">扫仓库、画架构、梳接口、列数据表</span> | AI 编码 Agent（如 Claude Code）         | <span style="color: red; font-weight: bold;">上下文管理（</span>准备接收项目信息）+ <span style="color: red; font-weight: bold;">能力扩展</span>（项目大就上 Sourcegraph MCP） | 沉淀到 CLAUDE.md      |
| 改一个小 bug        | 快速修复，不动其他                                                                   | AI 编码 Agent                        | 无                                                                                                                                                    | 给 AI 上下文，改完 review |
| 跨模块的中等改造        | 本系列大部分实战场景                                                                  | AI 编码 Agent + CLAUDE.md + SKILL.md | 测试框架 + CI                                                                                                                                            | 改造代码 + 测试          |
| 陌生项目 + 陌生语言     | 让 AI 既帮你理解项目又帮你学语言                                                          | AI 编码 Agent + CLAUDE.md            | MCP（GitHub / <span style="color: red; font-weight: bold;">Sourcegraph</span>）+ 语言学习助手模式                                                                                                                  | 项目理解 + 语言习得        |
| 高风险改造（安全、跨核心服务） | 容错空间小，必须找全调用路径                                                              | AI 编码 Agent + SKILL.md（专项技能）       | <span style="color: red; font-weight: bold;">Sourcegraph</span>（找全调用路径）+ <span style="color: red; font-weight: bold;">独立 review</span>（攻击者视角）                                                                                                                | 改造 + 多角度审查         |

观察这张表，第 2 章选型公式在这里得到了印证：**辅武器随场景复杂度单调递增**。改 bug 零辅武器；接手陌生项目第一天上上下文管理；跨模块中等改造加测试框架 + CI；高风险改造再加独立 review。配置按风险匹配，不是越多越好。

### 4.2 主战场详解：跨模块的中等改造

五个场景里哪个最值得深挖？第三个——跨模块的中等改造。它是本系列大部分实战的主战场，也是唯一能完整走通「三层骨架 + 主线工具」链路的场景。把这一场景拆开，三层骨架在工具层做了什么一目了然。

| 三层骨架 | 对应工具              | 在这一场景里做什么              |
| ---- | ----------------- | ---------------------- |
| 理解层  | CLAUDE.md         | 沉淀前几次改造中积累的项目理解        |
| 约束层  | <span style="color: red; font-weight: bold;">SKILL.md + 明确的提示词</span> | <span style="color: red; font-weight: bold;">写明本次改造的边界、不能动什么、改成什么样</span>  |
| 验证层  | 测试框架 + CI         | 改完跑测试、跑 CI，独立校验 AI 的产出 |

用传统软件工程的产物做对照，就能更好理解、快速对位：

| 三层骨架 | 传统工程里的对应物 | 共同本质 |
|---------|----------------|---------|
| 理解层（CLAUDE.md） | 团队长期积累的需求评审纪要 | 项目级共识常驻，新人（含 AI）自动加载，不用每次口头讲 |
| 约束层（SKILL.md + 提示词） | 改造前双方签字的接口契约 | 动什么、不动什么、改成什么样，白纸黑字 |
| 验证层（测试框架 + CI） | CI/CD 流水线上的自动门禁 | 不依赖人肉 review，AI 产出必须跑通才算数 |

> 第 03 篇三层骨架在工具层的落地：理解层靠 CLAUDE.md，约束层靠 SKILL.md，验证层靠测试框架 + CI。

这条引用是本章的关键判断：**武器组合不是工具堆砌，而是三层骨架在工具栈上的投影**。理解了这一点，遇到新场景先问「这三层分别要什么工具」，而不是「我要带什么工具」。

图里五个参与者：工程师（Eng）、Claude Code（CC）、CLAUDE.md（CMD）、SKILL.md（SKL）、MCP。用自然语言把时序复述一遍：

#### (1) 会话启动：自动加载项目上下文

会话一启动，Claude Code 自动加载 CLAUDE.md，不需要工程师干预。项目级上下文（架构共识、改造历史、约定）直接进入 AI 的工作记忆。这相当于新成员入职第一天，团队把评审记录和架构文档主动推到他面前，不用他自己翻。

#### (2) 工程师下达改造任务

工程师向 Claude Code 下达跨模块改造任务。任务描述要清楚，但项目背景不用重讲——CLAUDE.md 已经带了。

#### (3) 调用 SKILL.md：专项技能入场

Claude Code 收到任务后，按需调用 SKILL.md 里的专项技能（例如「画架构全景」），SKILL.md 返回规范化步骤告诉 AI 标准流程。这相当于调用团队沉淀的 SOP 文档——流程不用每次重写，照着走。

#### (4) 按需查 MCP：把代码之外的信息接进来

改造涉及跨仓库依赖或历史调用记录时，Claude Code 按需查 MCP，拿到代码本身看不到的依赖路径。注意时序图上的「按需」标记——MCP 不是每次都用，只在主线工具看不全时补位。

#### (5) 返回改造方案 + 代码 + 测试

最后，Claude Code 把改造方案、代码、测试一起返回。工程师拿到的不只是 diff，还有方案说明和验证手段，可以直接进 review 流程。

整条链路的关键特征是**自动加载 + 按需调用**：CLAUDE.md 自动加载不用催，SKILL.md 和 MCP 按任务需要才触发。工程师的工作量集中在两件事——下达清晰任务、review AI 产出。

### 4.4 为什么是这四件

最后一个问题：AI 工具那么多，为什么主线就这四件？答案藏在老项目改造的核心矛盾里——每一件主线工具都精准对位一个反复出现的痛点，少一件就有一个矛盾没人接。

| 工具 | 解决的老项目核心矛盾 | 不可替代性 |
|------|------------------|----------|
| Claude Code | 老项目复杂度 vs 工程师注意力带宽 | 主武器，AI 协作的入口 |
| CLAUDE.md | 上下文每次都要重讲 vs 项目知识应常驻 | 把项目理解固化到 AI 自动加载的位置 |
| SKILL.md | 反复出现的复杂操作 vs 每次重新描述 | 把操作流程沉淀成可复用的专项技能 |
| MCP | AI 只能看代码 vs 老项目依赖历史和跨仓库信息 | 按需把「代码之外的东西」接进来 |

四件工具、四个矛盾，互不重叠。

> <span style="color: red; font-weight: bold;">四件工具里前三件（Claude Code、CLAUDE.md、SKILL.md）必须吃透，MCP 用得相对较少。</span>其他工具——Sourcegraph、SonarQube、Cross-provider review——会在特定场景提到，但不是主线。

这是作者的实战判断：**吃透前三件，按需用第四件，其他工具按场景补位**。刚开始转型的话，优先把 Claude Code、CLAUDE.md、SKILL.md 用熟，MCP 等遇到跨仓库或历史信息缺口再上手。

## 5. 够用就停：为什么不用更多工具

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/617848a4bb20e1ed88606536dd9109f1_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

第 4 章正面回答了"为什么是这四件"。本章反过来回答一个更尖锐的质疑：既然 SDD 是趋势，Spec-Kit 和 OpenSpec 这两个明星工具为什么不在主线里？为什么不多挂几件工具让改造更省力？

这是"够用就停"这条心法的实战展开。

### 5.1 Spec-Kit 与 OpenSpec 不进主线

为什么不直接用 Spec-Kit 和 OpenSpec？这两个工具在 2026 年的 SDD 生态里几乎是默认选项。先看它们的定位，再看为什么这里刻意把它们排除在主线之外。

| 工具 | 定位 | 不进主线的原因 |
|------|------|--------------|
| Spec-Kit | GitHub 官方开源，流程重 | 适合从 0 到 1 做新项目，老项目改造强行套用流程重 |
| OpenSpec | 社区组件，相对 Spec-Kit 较轻 | 适合 brownfield / 改造，但这里想让读者深入细节、自己拆解项目 |

两个工具本身没问题。真正的冲突在于："用现成工具"和"学会怎么拆项目"在本文目标里互相排斥。这不是技术判断，是教学判断：

> <span style="color: red; font-weight: bold;">本文刻意尽量不用成熟工具，是为了让读者深入细节、亲手拆解项目。</span>这不是否定成熟工具的价值，是在"学方法论"和"用现成工具"之间优先选了前者。

学完之后，读者应该能拿着这套方法论回去用任何工具，而不是只会调参某一两个框架。道理像学开车——顺序是先手挡后自动挡。手挡逼你感受离合、油门、转速的配合，脚感练出来了，换自动挡只是减负担；反过来直接上自动挡，油门刹车踩得再熟，车怎么动起来依然是黑盒。工具栈同理：先用 Spec-Kit 这种"帮你把流程打包好"的框架，会跳过理解每一步为什么这么排的过程。先把 CLAUDE.md、SKILL.md、MCP 自己拆一遍，再回头用成熟工具——那时是驾驭，不是依赖。

### 5.2 多学一个工具的真实代价

"多学一个工具"听起来零成本——多记一个名字、多看一份文档。真代价是什么？

| 代价类型 | 具体表现 |
|---------|---------|
| 认知成本上升 | 学的时候觉得懂了，用的时候又发现模糊的地方 |
| 反复回查 | 真要用的时候记不清细节，反复查文档 |
| 注意力切碎 | 注意力被工具切碎，真正花在项目上的思考反而少了 |
| 肌肉记忆被稀释 | 老工具的熟练度被新工具的初学状态稀释 |

四类代价里最容易被低估的是最后一项——肌肉记忆稀释。学新工具的过程会不断干扰你对老工具的反射动作，原本闭眼能写的提示词，开始要回忆"是这个语法还是那个语法"。这指向一条更根本的判断：

> <span style="color: red; font-weight: bold;">工具数量不代表能力，熟练度才代表能力。</span>CLAUDE.md 闭着眼都能写、SKILL.md 看一眼就知道哪些该加、MCP 知道什么时候该接什么时候不该接——这些熟到不用思考，工程师的脑子才能留给项目本身。

工具学得精，注意力才能留给项目本身，这就是"够用就停"的本质。传统软件工程里这条规律早就成立：精通一个 Spring 比浅尝十个框架值钱，能讲清楚 IoC 容器生命周期、AOP 织入时机、事务传播行为的人，换到任何 JVM 框架都能快速上手；只学过十个框架"Hello World"的人，换一个项目就要从头再来。AI 工具栈同理——CLAUDE.md 写到能预测 AI 的反应、SKILL.md 调到能在不同项目复用，这种深度比多挂一个新 MCP 的边际价值高得多。

### 5.3 "够用就停"呼应"熬过冷启动"

这条"够用就停"的心法，和前面讲过的哪条心法呼应？

| 心法 | 出现位置 | 共同的本质 |
|------|---------|----------|
| 熬过冷启动 | 第 01 篇九步链路 | 老项目改造是长跑，前几步最慢，不要急 |
| 够用就停 | 本篇工具选型 | 老项目改造是长跑，节奏比花样重要 |

一条管时间维度——前几步慢是正常的；一条管工具维度——不急着扩展武器库。两条心法背后是同一个判断：老项目改造是长跑，不是冲刺。

> <span style="color: red; font-weight: bold;">老项目改造是个长跑，节奏比花样重要。</span>把那四件工具吃透之前，不要着急学更多。学完之后觉得不够，再去扩展——这是健康的学习路径。

这条不是"永远不学更多"，而是"先吃透再扩展"。判断扩展时机的标准很简单：当你用四件工具做完一两个真实改造，依然觉得少了什么，那时再引入第五件。如果在第一次改造之前就铺开一堆工具，连"够用"的基线都没建立起来，谈不上"停"。

这就是本章的反向校准：正面给出四件工具，反面解释为什么不加第五件。两面合起来，才是完整的工具选型决策。

## 6. 小结与思考

<img src="imgs/aicmigr-04-approach-04-ai-tools-overview/089f75ae90854f2fa06d188a6b503d6a_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

三句话浓缩全篇，再用一条逻辑链收住方法论基础，最后留两道思考题——把"地图"和"够用就停"从知识变成判断动作。

### 6.1 三句话浓缩

> **地图**：AI 编程工具按解决的问题分五类——AI 编码 Agent 是主武器，上下文管理、能力扩展、规范驱动开发（SDD）、工程辅助是四类辅助武器，每件工具都能对号入座。
>
> **用法**：主武器永远是 AI 编码 Agent，辅武器按场景复杂度加减。本系列主线是 Claude Code + CLAUDE.md + SKILL.md + MCP 四件，前三件必须吃透。
>
> **节奏**：工具数量不等于能力，熟练度才等于能力。四件吃透之前，不急着学更多。

地图、用法、节奏，正好对应传统软件工程里"用什么 / 怎么用 / 用到什么程度"的递进追问——这三问凑齐，单篇的工具地图就闭环了。

### 6.2 方法论基础的递进逻辑

把方法论基础四篇摆在一张图上看，它们是层层递进的：前一篇的结论，是下一篇的前提。

| 传统需求分析的关键问题 | 方法论基础的回答 |
|--------------------|------------------|
| 做什么（What） | 第 01 篇 九步链路 |
| 谁来做 / 做多少（Who / How much） | 第 02 篇 三档分工 |
| 怎么保证不跑偏（How to control） | 第 03 篇 三层控制 |
| 用什么做（With what） | 本篇 武器库地图 |

四问四答串起来的内在逻辑只有一句：**先想清楚做什么，再定 AI 做多少，然后给 AI 立规矩，最后挑趁手的工具——顺序错了，工具再多也救不回方向错误。** 工具是手段，方法论是方向；方向没立起来，学再多 Claude Code 技巧也只是 vibe coding 的高级形态。

这也是为什么本系列把方法论基础放在最前面，而不是上来就讲某个具体工具的实操。从下一篇开始，系列进入真实老项目的改造：九步链路的第一步、三档分工的第一档、三层骨架的第一层、武器库的第一件，都会在具体场景里逐一登场。读者会看到这四篇方法论不是孤立的概念，而是同一套动作在不同阶段的反复投影。

### 6.3 思考

两道题没有标准答案，目的是让读者把手上的工具组合对照本篇的地图自检一遍。

#### (1) 思考一

你现在常用的 AI 编程工具有几件？按本篇的五类划分，它们分别属于哪类？

逐件对号入座后，回答两个追问：

- 五类里，有没有哪一类你**完全没用过**，但可能应该用起来？
- 有没有同一类里你装了好几件，其实功能重叠、留一件就够？

这张自检表不是让你再多学几件，是让你看清手上的工具组合有没有缺口、有没有冗余。

#### (2) 思考二

回想最近学过、但一直没用起来的某个 AI 工具，把原因归到下面三类里的一类：

- **场景不匹配**：工具解决的不是你手头场景的问题。比如改造老项目时硬上 SDD，工具没错，是场景不对。
- **其实不需要**：工具解决的问题，你现有工具已经覆盖。比如又装一个上下文管理工具，但 CLAUDE.md 已经够用。
- **学得不够熟**：工具对路，只是还没吃透，遇到该用的场景反应不过来。

用本篇的武器库地图判断：当时该不该学它？答案是"不该学"，那不是你的问题，是工具海制造的焦虑；答案是"该学但没学熟"，就把这件工具拎出来，给它一点时间，练到不用思考就能上手。
