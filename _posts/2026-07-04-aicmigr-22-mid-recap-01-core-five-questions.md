## 1. 一句话定调：AI 是加速，不是兜底

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/58ab715d508f7eed8a3cad94c60314db_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

把老项目搬到 AI 协作时代，被问得最多的就是五个问题：这套思路到底有没有用？能不能直接抄？是不是每一步都得跟？为什么不用更高级的工具？照着跑完还是没效果，到底卡在哪？

这五个问题的答案，都指向同一句话——<span style="color: red; font-weight: bold;">AI 是加速，不是兜底</span>。

这句话每一个字都有分量。"加速"指的是体力活被压缩：写文档、扫代码、铺样板代码这些事，AI 干得又快又多。"兜底"指的是判断量：业务方向对不对、边界场景怎么定、方案能不能过，这些 AI 给不了答案，只能你自己扛。

下文所有内容都围绕这个区分展开。先把"哪些变了、哪些没变"讲清楚，再把五个问题逐个回答，最后把能直接用的 Check List 留给你贴进项目仓库。

## 2. 变与不变：先把根概念搭起来

### 2.1 老项目改造的本质只有两件事


<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/cb6893dca47746b1846597b6efdf5f8b_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">


不管用不用 AI，老项目改造说到底就两件事：<span style="color: red; font-weight: bold;">理解 + 开发</span>。

接到一个改造任务，顺序永远是：<span style="color: red; font-weight: bold;">先理解项目（架构、依赖、约束、历史包袱）→ 再理解这次要改的需求（业务目标、边界、影响）→ 最后才能开发（写代码、补测试、改文档）。这个流程从有软件工程那一天起就是这样，AI Coding 改不了它。</span>

### 2.2 变的不是流程，是工序分工

那 AI Coding 到底改变了什么？<span style="color: red; font-weight: bold;">流程没变，变的是流程里每一步由谁来执行</span>。

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/6d0e069218541feaee345c8f6981e502_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

打个传统软件工程的类比：瀑布模型搬到敏捷，开发阶段还是那几个（设计→编码→测试→集成），变的是每个阶段谁主导、节奏多快、怎么反馈。AI 协作是同一种变化——工序还是那些工序，只是某些步骤从"人来做"变成了"AI 来做、人来审"。

### 2.3 70% 加速 vs 30% 兜底：一张表分清楚

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/0658dc02fac3166e82577be4b458028c_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

理解了"变的是分工"，就能把方法论的核心心法落到一张表上。这套系列的全部工作，就是把表里这两栏分清楚、各管各的。

| 加速部分（AI 替你压缩的 70% 体力活） | 兜底部分（必须人自己扛的 30% 判断量） |
|------|------|
| 写需求文档：一句话需求铺成 PRD 草稿 | 业务目标的方向（拆需求判断一） |
| 摸现有代码：扫一遍出影响面、列改动点 | 边界场景的产品决策（拆需求判断二） |
| 写改造方案：画图、列改造点、出 solution.md 草稿 | 不在这次范围里的事（拆需求判断三） |
| 写代码：按改造点清单逐条落实 boilerplate | 改造前的现状确认（翻车教训） |
| 写测试：覆盖大部分边界，Characterization Test 也能起草 | 方案第 7 节决策点审核（拆方案 Step 7） |
| 写文档：同步更新 docs/ 与 CLAUDE.md | 测试断言凭实际不凭应该 |
|  | 最终代码 review（后端开发篇） |

把 70% 的体力活交给 AI 压缩，把 30% 的判断量自己扛住，整套方法论就稳了。<span style="color: red; font-weight: bold;">流程化是为了帮你压缩体力活，不是为了让你 100% 当甩手掌柜。</span>判断量没下来，思考量必须自己保证。

根概念搭到这里，下面进入五个问题的具体回答。

## 3. 五问之一：这套思路真的有用吗

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/ec3a0f5727a2b61bb16b37304c772eb2_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

### 3.1 你可能会问：自己摸索不也能做出来吗

能，但<span style="color: red; font-weight: bold;">质量不稳定</span>。

状态好的时候，需求文档面面俱到，改造一遍过；状态差的时候（被打断、赶进度、临时换需求），漏掉三个边界、踩了两个禁区，都是常有的事。自己摸索的上限很高，下限也很低。

### 3.2 方法论解决的不是"做不做得出来"

它要解决的是<span style="color: red; font-weight: bold;">稳定——每次做出来都至少在 80 分以上</span>。

做法说穿了很简单：**流程化、标准化**。<span style="color: red; font-weight: bold;">把"考虑某个边界"这件事从脑子里移到文档里。脑子会累、会忘、会被打断，文档不会。</span>把每一步——谁该做什么、什么时候人停下来介入、什么时候 AI 自主跑、做完怎么验证——标准化成一套可复用的流程。

所以思路有用，有用在它不是教你新知识，而是<span style="color: red; font-weight: bold;">让质量不再依赖个人状态</span>。

## 4. 五问之二：能直接抄吗

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/816839143f6f5a18e22cef78f35e3f07_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

### 4.1 第一反应都是"好繁琐"

一个改造任务被拆成需求文档、改造方案、影响分析、改造点清单、改造步骤、决策点审核，跑下来好几个文档。这看起来比"凭经验直接搞"慢得多。

但这种比较是错的——它拿"流程的显式成本"去比"凭经验的隐性成本"。

### 4.2 "凭经验直接搞"的真实成本

回想一下凭经验做的真实场景：

- 写到一半发现某个边界没考虑，回头改；
- 业务方一看"不是我要的"，需求重新对齐；
- 改完发现某个老接口被破坏了，紧急回滚；
- 上线后某个 SDK 客户报错，凌晨修。

这些时间加起来，比"按流程跑一遍"多得多。<span style="color: red; font-weight: bold;">流程不是凭空增加成本，是把分散在反复返工里的成本集中显式化，让你提前看见、提前决策。</span>

### 4.3 慢就是快

跑过一遍完整流程后，下次拿到类似改造，心里会有底很多。不是因为流程多神奇，是因为**该想的地方都想过了、该确认的地方都确认过了**。老项目改造这种场景，需要的恰恰就是这种繁琐、流程、标准——这才是质量的保证。

所以可以直接抄，作者自己也一直这么用，效果挺好。前提是先认同一个心法：<span style="color: red; font-weight: bold;">慢就是快</span>。

## 5. 五问之三：必须 100% 跟流程吗

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/5d728d38c27b1eccd62e29970e302ced_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

### 5.1 杀鸡用不着牛刀

整套流程是为"涉及多模块、多人协作、有历史包袱"的改造设计的。下面这些场景，凭经验直接搞就行，不必走全套流程：

- 修一个明确的 bug（需求清楚、边界明确）；
- 改文案、调样式；
- 重构一段独立的工具函数；
- 加一个内部脚本。

### 5.2 这些场景强烈建议跟流程

但如果你的改造命中下面任何一条，强烈建议跟流程——"凭经验直接搞"的失败成本在这里非常高：

- 涉及多个模块、多个 service 协同；
- 涉及前后端联动；
- 老接口有外部依赖（SDK 客户、其他系统）；
- 多人协作开发同一个特性；
- 有历史包袱（CLAUDE.md 里写了禁区那种）。

### 5.3 跑熟了流程会内化成肌肉记忆

还有一件事要说明：流程的目的不是让你永远依赖它，是让你养成肌肉记忆。

跑过 5-10 次完整流程后，你不再需要每次打开提示词清单照抄。心里会有一份自己的清单，自己走完关键步骤：

- 拿到需求先想三件事：业务目标、边界场景、不在范围里的事；
- 动手前先想两件事：影响范围、关键决策点；
- 改完代码后必须做：跑测试、看 git diff、检查老代码有没有被顺手改。

### 5.4 一句话总结

<span style="color: red; font-weight: bold;">复杂改造跟流程，简单改动凭经验，跑熟了流程会内化。</span> <span style="color: red; font-weight: bold;">判断标准就是失败成本——改崩了影响小、能快速回滚的，凭经验；改崩了一片、回滚代价大的，跟流程。</span>

## 6. 五问之四：为什么没用高级 AI 工具

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/cb656c70bd0da0995f2b47a319845a22_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

### 6.1 系列的核心是工作流，不是工具

你可能会问：怎么一直没讲 Cursor、Cline、Aider 这些新工具？

因为<span style="color: red; font-weight: bold;">工具年年换，工作流很稳定</span>。今年红的是 Cursor，明年可能是别的。但老项目改造的工作流本质，跨工具、跨技术栈、跨团队都成立：

- 理解项目（看代码 + 看文档 + 问业务）；
- 拆需求（六维 + 边界 + 决策）；
- 拆方案（链路 + 改造点 + 影响）；
- 改代码（小步 + 测试 + review）；
- 沉淀（资产更新 + 教训写进 CLAUDE.md）。

读者要带走的是这套工作流，不是某个工具的快捷键。

### 6.2 系列其实用了不少朴素工具

回头看，系列用到的工具不少，只是它们不被叫做"高级 AI 工具"：

| 工具 | 作用 |
|------|------|
| CLAUDE.md | 项目级约束注入 |
| SKILL | 可重复流程的固化 |
| docs-auto-sync | 文档同步 SKILL |
| Characterization Test | 行为锁定 |
| CI | 自动护栏 |
| deps-start.sh | 环境一键启动 |

这些都是工具，但都是朴素的、围绕工作流补位的工具。它们不靠 marketing，靠"真的解决问题"。

### 6.3 工作流为先，工具补位

工具是为需求服务的，不是反过来为了用工具而硬塞进流程。在系列的流程里，暂时没有发现哪个步骤特别需要某个高级 AI 工具。

我的立场很明确：<span style="color: red; font-weight: bold;">如果将来跑某个改造，发现某个工具能让某一步快十倍，会引入它；但绝不会反过来为了用上某个工具而硬塞进流程。</span>

## 7. 五问之五：照着跑完没效果，问题出在哪

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/f6c0a26ac2fce3b5adb742e3e906da85_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/9936ddf12bc165e04b6c5eeab9f49d50_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

这是五个问题里最值钱的一个，必须看完。

如果你按流程跑了一遍，效果还是不好，<span style="color: red; font-weight: bold;">99% 的情况只有一个原因：该停的地方没停</span>。

老项目改造里有几个关键的停顿点，AI 不能替你做、必须人停下来想清楚。这些点在流程里被反复强调过，但跑流程的时候很容易被 AI 带快了节奏，导致该停的时候没停。

下面是三个最常见的显性失败模式，加一种更隐蔽的隐性失败。每一种都给出自查方法——你回头看自己的项目，就能判断是不是这一类。

### 7.1 失败模式一：拆需求时偷懒

**具体表现**：

- 业务目标方向直接用 AI 写的，没自己改；
- 边界场景的"待产品决策"没去问产品，直接让 AI 默认填一个；
- "不在这次范围里的事"没拍板，AI 列了 8 条就 8 条。

**结果**：需求文档看起来全，实际方向是偏的。后端开发做完代码，业务方一看"这不是我要的"。

**自查方法**：

| 自查项 | 偷懒的信号 |
|------|------|
| 业务目标这一节 | 是 AI 写的还是你写的？ |
| 边界场景每条后面 | 有没有你拍板的产品决策（不是 AI 推断的）？ |
| "不在这次范围里" | 是只有候选，还是有最终决策？ |

### 7.2 失败模式二：跳过 Step 7 决策点审核

**具体表现**：

- AI 跑完六步出了 solution.md 草稿；
- 你扫了一眼觉得挺全的，没认真审第 7 节"待审核的关键决策点"；
- 直接进入后端开发。

**结果**：方案有隐性问题没暴露。比如这次改造有破坏性 props 变更（D2 决策），AI 已经标在第 7 节了，你没看到，后端开发改完，前端发现调用方全挂。

**自查方法**：solution.md 第 7 节的每条决策，你是真的看了、给了判断，还是直接 OK 让 AI 整理定稿。

### 7.3 失败模式三：跳过现状确认

**具体表现**：

- 拿到需求直接进入拆需求；
- 没先打开产品点几下确认现状；
- 跟着流程跑了一圈才发现功能本来就有。

**结果**：这个最致命，整个 4 小时的工作量直接归零——做了一个本来不需要做的功能。

**自查方法**：开工前你自己有没有点过产品？还是只看了 AI 扫代码的输出？

> 为什么要强调"点产品"而不只看 AI 扫代码？因为代码层有实现，不代表产品层有入口。AI 通过 Controller / Service 方法判断功能是否存在，对企业项目里"同名能力多个实现路径"的场景容易漏判。

### 7.4 隐性失败：不够细心，漏掉细节

上面三个失败模式比较显性，自己回头看一眼就能发现。但还有一种更隐蔽的：**完整跑了流程，每步都没明显偷懒，效果还是平平**。

可能的原因：

- **不够细心**：AI 给的某个判断你心里有疑虑，但没追问，让它过去了；
- **漏掉细节**：某个 review 重点没逐字看，AI 偷偷塞了个不一致的实现。

处理方式只有一个：<span style="color: red; font-weight: bold;">慢一点、更细一点</span>。

这背后的心法是——AI 在数据/代码层面强，在判断层面弱。反过来意味着：<span style="color: red; font-weight: bold;">你在判断层面的每一次"算了不追问了"，都是流程的漏洞。</span>

### 7.5 一句话收口

<span style="color: red; font-weight: bold;">工作量下来 ≠ 思考量下来。</span>

这是 AI 协作里最容易混淆的两个概念。<span style="color: red; font-weight: bold;">流程化的目的，是让你把省下的体力和时间用在该思考的地方：业务判断、产品决策、现状确认、深度 review。</span>

<span style="color: red; font-weight: bold;">如果你节省的时间没有用在思考上，你就只是在更快地走错路。</span>

## 8. 可直接复用的 Check List

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/a8cbee69c535596fac405910b598045b_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/e338e0057ccdda192e62cc6eef1f7c69_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/9716906ec15acefb95ab0da257ce393c_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

这一章把前面所有方法论裁剪成一份可直接复用的 Check List，按改造流程的时序组织：开工前 → 拆需求 → 拆方案 → 改代码 → 沉淀。每一节里的"必做"是硬约束，跳过会显著抬高失败成本；"建议"按场景判断是否需要做。可以单独摘出来贴到项目仓库里随时翻阅。

### 8.1 开工前：现状确认（必做）

| 必做项 | 为什么 |
|------|------|
| 打开产品点几下确认现状 | 代码层有实现 ≠ 产品层有入口，AI 容易漏判"同名能力多实现路径" |
| 判断立项方向（新增 / 重构 / 优化） | 功能不存在→新增；实现不符预期→重构；性能体验差→优化 |
| 把现状写进需求文档第一节 | 避免协作者重复确认，避免跑完才发现本来就有 |

### 8.2 拆需求：六维 + 三个判断（必做）

AI 出六维草稿后，下面三个判断**必须人来拍板**：

| 判断 | 必须人做的部分 |
|------|------|
| 业务目标方向 | 自己改，不能直接用 AI 写的 |
| 边界场景产品决策 | 每条后面要有产品决策，"待产品决策"必须去问产品 |
| 不在这次范围里的事 | 必须拍板最终范围，不能 AI 列了 8 条就 8 条 |

**自查**：回头看你的需求文档——业务目标是你写的还是 AI 写的？边界场景每条后面有没有你拍板的产品决策？"不在这次范围里"是只有候选还是有最终决策？

### 8.3 拆方案：七步法 + Step 7 审核（必做）

AI 跑完六步出 solution.md 草稿后，**第 7 节必须认真审**。

第 7 节"待审核的关键决策点"是方案可能踩坑的地方集中展示，包括破坏性 props 变更、对外接口契约变更等。AI 已经标了，但是否通过**必须人给判断**。

**自查**：第 7 节的每条决策，你是真的看了、给了判断，还是直接 OK 让 AI 整理定稿？跳过这一步最常见后果——改完前端发现调用方全挂。

### 8.4 改代码：小步 + 测试 + review（必做）

改完代码必须做三件事：

- 跑测试；
- 看 git diff；
- 检查老代码有没有被顺手改（特别是被 AI 顺手改）。

另外两条必做约束：

- <span style="color: red; font-weight: bold;">测试断言凭实际不凭应该：Characterization Test 的断言要锁定现状，而不是"应该有的样子"。如果断言凭"应该"写，等于自己骗自己，回滚时都不知道哪里被破坏了。</span>
- **最终代码 review 不能省**：AI 写的大部分 boilerplate 看着像对的，但细节可能偷偷塞了个不一致的实现。对有疑虑的判断要追问，不能"算了让它过去"。

### 8.5 沉淀：资产更新 + 教训写进 CLAUDE.md（建议）

| 建议项 | 收益 |
|------|------|
| 更新 docs/ 资产（接口清单、数据模型、链路图、改造点清单） | 下次 AI 扫这些资产时拿到的就是最新版本 |
| 教训写进 CLAUDE.md（踩过的坑、新增禁区、新总结规范） | 下次 AI 协作时自动避坑 |

补充一条贯穿全程的原则：<span style="color: red; font-weight: bold;">工作流为先，工具补位</span>。如果某一步发现某个工具能让它快十倍，引入它；但不要反向硬塞工具进流程。

### 8.6 流程裁剪：判断是否走全套

| 不需要走全套流程 | 强烈建议跟流程 |
|------|------|
| 修一个明确的 bug（需求清楚、边界明确） | 涉及多个模块、多个 service 协同 |
| 改文案、调样式 | 涉及前后端联动 |
| 重构一段独立的工具函数 | 老接口有外部依赖（SDK 客户、其他系统） |
| 加一个内部脚本 | 多人协作开发同一个特性 |
|  | 有历史包袱（CLAUDE.md 里写了禁区那种） |

## 9. 小结与思考

<img src="imgs/aicmigr-22-mid-recap-01-core-five-questions/21e062ff305f48de532bb867967cdc00_MD5.jpg" style="display: block; width: 800px;" alt="替换文字">

### 9.1 五个问题的一句话答案

| 问题 | 答案 |
|------|------|
| 思路有用吗 | 老项目改造本质是"理解 + 开发"，AI Coding 只改了工序分工；方法论解决的是稳定性，让每次都在 80 分以上 |
| 能直接抄吗 | 慢就是快，流程不等于繁琐——它把隐性返工成本显式化 |
| 必须 100% 跟流程吗 | 复杂改造跟流程，简单改动凭经验，跑熟了流程会内化 |
| 为什么没用高级 AI 工具 | 工作流为先、工具补位，系列用了不少朴素工具，没用高级工具是因为没必要 |
| 效果不好的根本原因 | 该停的地方没停——三个显性失败模式加一种隐性失败 |

最值得记牢的还是那句贯穿全文的话：<span style="color: red; font-weight: bold;">工作量下来 ≠ 思考量下来</span>。

### 9.2 思考

**(1) 哪个失败模式最戳到你？**

回头看你最近一次跑流程的体验，是不是真的在某个地方该停没停？是拆需求偷懒了、跳过 Step 7 了，还是没做现状确认？

**(2) 你怎么理解"工作量下来 ≠ 思考量下来"？**

AI 帮你省下来的时间，你最近一次具体用在哪里了——是用在了业务判断、产品决策、现状确认、深度 review 上，还是只是更快地把活干完了？
